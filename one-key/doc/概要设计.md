# 产品概要设计

## 1. 产品名称（暂定）

**透明本地保险箱（Transparent Local Vault）**

> 一个以“透明”为第一原则、以“本地化”为核心实现方式的密码与凭证管理工具。

---

## 2. 产品定义

### 2.1 核心定位

本产品首先解决的不是“密码存在哪里”，而是：

> **用户能够明确知道自己的敏感凭证如何被保存、如何被保护、是否联网、是否上传，以及应用在做什么。**

在此基础上，提供完全本地化的密码管理能力。

产品优先级：

1. **透明**
2. **本地化**
3. **密码管理基本能力**
4. **现代凭证兼容，包括 Passkey**
5. **易用性**

### 2.2 核心价值主张

- 无需注册账号
- 无需依赖云端
- 默认不上传密码或凭证
- 本地保险箱文件位置明确可见
- 加密方式、随机生成方式、网络权限可查看
- 代码公开、可审查
- Password 与 Passkey 统一围绕“账户”管理
- 用户能理解密码强度，而不是只看到技术参数

---

## 3. 产品原则

### 3.1 透明优先

产品中的关键安全行为均应可被用户理解和检查。

包括：

- 数据保存位置
- 是否联网
- 是否同步
- 密码生成方式
- 保险箱加密方式
- 自动锁定状态
- 剪贴板清理状态
- 当前应用版本
- 当前构建版本 / Commit
- 源代码入口

透明不是“高级设置”，而是产品体验的一部分。

### 3.2 Local First

默认模式：

```text
用户
 ↓
本地应用
 ↓
本地加密保险箱
```

不存在：

```text
账号系统
云端密码数据库
后台同步
用户行为上传
第三方密钥托管
```

### 3.3 不自创密码学协议

使用成熟、公开、可审查的密码学方案与实现。

产品负责：

- 正确集成
- 明确表达
- 缩小安全边界

而不是设计新的密码算法。

### 3.4 账户优先，而不是凭证类型优先

核心对象是：

```text
账户
├── 用户名 / 邮箱
├── Password
├── Passkey
├── URL
├── 自定义字段
└── 备注
```

Password 和 Passkey 都属于账户的凭证。

## 4. 目标用户

### 4.1 首要目标用户

- 重视隐私与数据自主权的个人用户
- 不希望使用云端密码同步服务的用户
- 对安全工具有一定认知，但不希望使用复杂工具的用户
- 需要管理多个网站、服务、开发账户的用户

### 4.2 非目标用户

MVP 暂不面向：

- 大型企业
- 团队权限管理
- 企业 SSO
- 多租户 SaaS
- 密钥审批流
- 审计合规平台

## 7. 密码生成器设计

### 7.1 MVP 不做平台规则匹配

当前版本不包含：

- GitHub 密码规则推荐
- Google 密码规则推荐
- 平台域名识别
- 平台模板库
- 自动匹配密码策略

原因：

- 降低首版复杂度
- 避免维护平台规则数据库
- 优先验证密码管理核心价值
- 保持功能透明、可控

后续如果用户验证存在明确需求，再独立设计 Password Policy Registry。

### 7.2 自定义生成模式

默认界面：

```text
密码长度        20

字符类型
✓ 大写字母 A-Z
✓ 小写字母 a-z
✓ 数字 0-9
✓ 符号

[ 重新生成 ]
```

### 7.3 高级设置

建议收纳在二级区域：

```text
高级设置 >
```

包括：

- 排除相似字符
  - O / 0
  - I / l / 1
- 自定义允许符号
- 至少包含一个大写字母
- 至少包含一个小写字母
- 至少包含一个数字
- 至少包含一个符号

后续可扩展：

- 首字符不能为符号
- 尾字符不能为符号
- 自定义排除字符
- Passphrase 模式

### 7.4 随机生成原则

禁止使用：

```text
Math.random()
```

必须使用密码学安全随机源。

Web / TypeScript 环境：

```text
crypto.getRandomValues()
```

Rust Core：

```text
OS CSPRNG
```

用户默认不需要理解 CSPRNG，但可以在“安全详情”中看到：

> 此密码由操作系统提供的安全随机数生成，不依赖网络。

## 8. 密码强度设计

### 8.1 为什么必须表达强度

用户不应只看到：

```text
20 位
大小写
数字
符号
```

而应该能够直接理解：

> 这个密码到底安不安全。

### 8.2 用户层表达

建议采用四级：

```text
弱
一般
强
很强
```

示例：

```text
abc123
弱

容易被猜测，建议使用更长的随机密码。
```

```text
Hello2026!
一般

长度尚可，但存在明显可预测结构。
```

```text
N8#uZ4!qT2$pxF7@Km3L
很强

随机生成，长度充足，字符组合丰富。
```

### 8.3 不使用“字符类型数量”作为唯一判断

以下密码即使同时包含：

- 大写
- 小写
- 数字
- 符号

也不能直接判定为强密码：

```text
P@ssw0rd123!
```

强度分析至少应识别：

- 常见密码
- 单词变形
- 连续数字
- 连续字母
- 键盘序列
- 重复模式
- 日期模式
- 用户可预测结构

### 8.4 区分系统生成密码和用户输入密码

#### 系统生成密码

已知来源是密码学安全随机数，因此可以结合：

- 长度
- 字符集规模
- 随机性
- 理论 entropy

计算强度。

#### 用户输入密码

不能假定随机。

必须通过模式分析进行评估。

代码结构建议：

```text
generator/
strength/
crypto/
```

分别负责：

- 生成
- 强度评估
- 保险箱加密

禁止将三个概念混为一个“密码安全算法”。

### 8.5 强度 UI

默认：

```text
密码

N8#uZ4!qT2$pxF7@Km3L

安全强度
██████████
很强

随机生成 · 20 位
```

安全详情：

```text
安全详情

生成方式
操作系统安全随机数

长度
20

字符集
大写 / 小写 / 数字 / 符号

估算随机强度
约 xxx bits

网络请求
无
```

### 8.6 强度实现建议

优先考虑成熟密码强度评估库或成熟思路，不自行设计“安全评分公式”。

重点不是得到一个绝对精确的数值，而是：

- 避免误判
- 提供用户可理解的信息
- 提供明确改善建议

## 9. Passkey 兼容设计

### 9.1 产品层定义

产品不是单纯 Password Manager。

更准确的模型：

> **Local Credential Vault**

账户可以同时存在：

```text
GitHub

用户名
cd@example.com

登录凭证

✓ Password
✓ Passkey
```

### 9.2 V0.1

V0.1 需要：

- 数据模型兼容 Passkey
- UI 中允许显示未来 Passkey 区域
- 数据格式支持版本升级

但暂时不要求：

- 创建 Passkey
- WebAuthn 拦截
- 浏览器自动登录
- 浏览器扩展

### 9.3 Passkey 数据模型

概念模型：

```ts
interface PasskeyCredential {
  credentialId: string
  rpId: string
  rpName?: string

  userHandle?: string
  userName?: string

  algorithm: number

  privateKeyEncrypted: string

  createdAt: number
}
```

私钥必须属于保险箱的加密范围。

### 9.4 后续完整 Passkey 路线

完整支持需要：

```text
Website
 ↓
WebAuthn
 ↓
Browser
 ↓
Browser Extension
 ↓
Native Messaging
 ↓
Desktop Vault
 ↓
Passkey Private Key
```

因此建议：

```text
V0.1
数据模型兼容

V0.2 / V0.3
浏览器扩展

V0.3+
完整 Passkey 创建与登录
```

### 9.5 Passkey 与本地化的风险

本地 Passkey 的私钥如果丢失：

```text
保险箱丢失
+
没有备份
=
Passkey 丢失
```

因此 Passkey 上线前，“本地备份”必须成为正式能力。

用户必须明确看到：

> 此 Passkey 仅保存在本地保险箱中。如果保险箱文件丢失且没有备份，你可能无法再使用此 Passkey 登录。

## 11. 本地保险箱设计

### 11.1 基本结构

建议 V0.1 使用单个加密文件：

```text
vault.localvault
```

逻辑结构：

```text
Header
├── formatVersion
├── salt
├── KDF parameters
├── cipher parameters
└── encrypted payload
```

解密后：

```json
{
  "version": 1,
  "entries": [],
  "settings": {}
}
```

### 11.2 为什么首版优先单文件

优点：

- 容易理解
- 容易备份
- 容易迁移
- 容易复制
- 安全边界小
- 加密边界清晰
- 不需要设计字段级加密策略

### 11.3 主密码

基本流程：

```text
Master Password
+
Random Salt
 ↓
Argon2id
 ↓
Vault Key
 ↓
AEAD Encrypt / Decrypt
```

原则：

- 不保存主密码
- 不直接 Hash 后当加密密钥
- 不自创 KDF
- 锁定后尽量清除敏感内存

## 12. 建议数据模型

```ts
interface Vault {
  version: number
  entries: AccountEntry[]
  settings: VaultSettings
}

interface AccountEntry {
  id: string

  title: string

  urls: string[]

  identity?: {
    username?: string
    email?: string
  }

  credentials: {
    password?: PasswordCredential
    passkeys?: PasskeyCredential[]
  }

  customFields?: CustomField[]

  notes?: string

  tags?: string[]

  createdAt: number
  updatedAt: number
}

interface PasswordCredential {
  value: string

  createdAt: number
  updatedAt: number
}

interface CustomField {
  id: string
  name: string
  value: string
  secret?: boolean
}

interface VaultSettings {
  autoLockSeconds: number
  clipboardClearSeconds: number
}
```

## 17. 产品验证重点

MVP 不以“下载量”为最核心指标。

更重要的是用户是否真的把敏感数据迁入产品。

建议观察：

### 核心指标

- 创建保险箱比例
- 创建第一个账户比例
- 导入 / 创建超过 10 条账户比例
- 7 日再次解锁率
- 30 日留存
- 平均账户数量
- 密码生成器使用次数
- 密码复制次数
- 自定义字段使用率
- 备注使用率

### 产品价值验证

重点回答：

1. 用户是否理解“透明本地保险箱”？
2. 用户是否因为“不联网、不上传”而选择本产品？
3. 用户是否愿意真正迁移密码？
4. 用户是否认为现有 KeePass 类产品过于复杂？
5. 密码强度说明是否真正帮助用户做决定？
6. 用户是否强烈要求浏览器自动填充？
7. 用户是否强烈要求手机端？
8. 用户是否真实需要 Passkey？

## 18. 主要风险

### 18.1 产品风险

最大风险不是技术实现，而是：

> 用户认为 KeePassXC 已经足够。

因此差异化不能只停留在：

```text
本地
+
开源
```

应该强化：

```text
透明
+
现代体验
+
低学习成本
+
安全能力可理解
```

### 18.2 安全风险

需要重点防范：

- 主密码过弱
- Vault 文件被窃取
- 内存中的解密数据
- 剪贴板泄露
- 本地恶意软件
- 恶意浏览器扩展
- 备份文件泄露
- Passkey 私钥丢失

### 18.3 “透明”与“复杂”的冲突

不能为了透明，在主界面展示过多：

```text
Argon2
AEAD
Entropy
Nonce
Salt
```

正确方式：

```text
第一层：用户能理解
第二层：技术用户能验证
第三层：源码可审查
```

## 19. 产品一句话定义

推荐：

> **一个透明、完全本地的密码与凭证保险箱，让用户清楚知道自己的密码在哪里、如何被保护，以及应用究竟做了什么。**

更短版本：

> **你的密码，只在你看得见的地方。**

产品内部原则：

> **Transparent First. Local by Default.**
