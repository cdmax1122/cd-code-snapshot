# 透明本地保险箱 — 架构设计（uni-app x）

## 1. 架构目标

本项目采用 **uni-app x** 作为跨端应用框架，目标是在一套核心产品逻辑下支持：

- iOS App
- Android App
- 后续 HarmonyOS
- Web 非敏感功能
- 微信小程序非敏感功能

但遵循一个重要原则：

> **跨端复用 UI 和业务逻辑，不强行跨端复用敏感安全实现。**

即：

```text
跨端 UI / 普通业务
        ↓
     uni-app x

安全敏感能力
        ↓
UTS / 系统原生能力
```

uni-app x 的 UTS 可以直接调用 Android、iOS、HarmonyOS 原生 API，官方也建议将平台原生 API 调用封装到 UTS 插件中，因此适合作为本项目“跨端 UI + 原生安全核心”的基础框架。

---

# 2. 核心架构原则

## 2.1 Transparent First

透明是产品第一原则。

架构需要能够回答：

```text
数据存在哪里？

数据有没有上传？

谁可以读取 Vault？

密码如何生成？

Vault 如何加密？

Passkey 私钥在哪里？

App 是否联网？

当前代码对应哪个构建版本？
```

这些信息不能只存在技术文档中，需要能够在产品中展示。

---

## 2.2 Local First

核心 Vault 只存在用户设备。

默认数据流：

```text
用户
 ↓
App
 ↓
本地安全模块
 ↓
Encrypted Vault File
```

默认不存在：

```text
App
 ↓
HTTP API
 ↓
Cloud Vault
```

MVP 目标：

```text
密码数据网络请求 = 0
```

---

## 2.3 Native Security Boundary

以下能力禁止简单作为普通 Vue 页面逻辑实现：

```text
Vault Key
Master Password
Vault Encryption
Passkey Private Key
Biometric Unlock
Secure Storage
```

它们统一进入：

```text
Native Security Layer
```

UI 不应该知道加密细节。

---

## 2.4 Account First

数据不是：

```text
password[]
passkey[]
```

而是：

```text
Account
│
├── Identity
├── Password
├── Passkeys
├── URL
├── Custom Fields
└── Notes
```

这样 Password 和 Passkey 可以自然共存。

# 5. 分层职责

## 5.1 Presentation Layer

技术：

```text
uni-app x
UVUE
UTS
```

负责：

- 页面
- 表单
- 状态显示
- 用户输入
- 动画
- Password Strength 展示
- Vault 状态展示

禁止：

- 自己实现 Vault 解密
- 长期持有 Vault Key
- 直接保存 Master Password
- Passkey 私钥处理

例如页面只调用：

```ts
await vaultService.unlock(password)
```

而不是：

```ts
const key = argon2(password)
const data = decrypt(vault, key)
```

# 10. Vault 文件设计

建议：

```text
xxx.localvault
```

结构：

```text
┌─────────────────────────┐
│ Header                  │
│                         │
│ magic                   │
│ formatVersion           │
│ KDF config              │
│ salt                    │
│ cipher config           │
│ nonce                   │
├─────────────────────────┤
│                         │
│ Encrypted Payload       │
│                         │
│ Account                 │
│ Password                │
│ Passkey                 │
│ Notes                   │
│ Settings                │
│                         │
├─────────────────────────┤
│ Authentication Tag      │
└─────────────────────────┘
```

原则：

> 除必要的加密元信息之外，账户数据全部进入加密 Payload。

不要出现：

```text
github.com     明文
username       明文
title          明文
password       密文
```

否则会泄露大量 metadata。

# 11. Vault 加密流程

推荐逻辑：

```text
Master Password
        │
        │ + Salt
        ↓
     Argon2id
        │
        ↓
   Derived Key
        │
        ↓
   Vault Key / KEK
        │
        ↓
AEAD Encrypt / Decrypt
```

实际密码学实现应该进一步经过专门的安全设计与审查。

MVP 设计原则：

- KDF：成熟实现
- Encryption：AEAD
- 每个 Vault 独立随机 Salt
- Nonce 正确管理
- 不保存 Master Password
- 不把 Master Password 写入日志
- 不进入持久化 Store
- 锁定后清理 Session

# 13. 为什么使用 UTS Native Plugin

uni-app x 官方目前允许 UTS 直接使用 Android、iOS、HarmonyOS 的平台原生 API，并建议把这类调用封装为 UTS 插件。

同时 uni-app x 原生 SDK 能将应用资源生成对应的 Kotlin、Swift、ETS 等代码，并与原生工程协同调试，因此后续如果安全模块需要深度原生实现，不需要推翻整个 UI 架构。

因此架构选择：

```text
普通产品逻辑
UTS / uni-app x

↓

安全系统能力
UTS Plugin

↓

必要时
Swift / Kotlin 原生 SDK
```

而不是强求：

```text
100% UTS
```

# 15. Secure Random 抽象

禁止：

```ts
Math.random()
```

设计：

```ts
interface SecureRandomProvider {
  nextBytes(length: number): Uint8Array
}
```

App：

```text
Operating System
     ↓
SecureRandomProvider
```

Web：

```text
crypto.getRandomValues()
```

Generator 本身只负责算法：

```text
Generator
    ↓
SecureRandomProvider
```

这样随机数来源可以独立审查。

# 26. Clipboard

Clipboard 是一个明确的安全边界。

复制：

```text
Vault
 ↓
Clipboard
 ↓
30 sec
 ↓
Clear
```

实现必须考虑：

```text
用户复制密码 A

↓

20 秒后用户又复制了普通文字 B

↓

Vault 不应该清除 B
```

所以应该记录：

```text
clipboard fingerprint
```

清理时：

```text
如果当前 clipboard
仍然等于 Vault 写入值

↓

clear
```

否则：

```text
do nothing
```

# 35. Error Handling

安全错误不要泄露敏感内部状态。

例如：

```text
解锁失败

主密码错误或保险箱无法解密
```

不要展示：

```text
AES authentication tag invalid at block...
```

技术信息可写入：

```text
本地诊断日志
```

且不得包含明文凭证。

# 42. Threat Model

MVP 至少明确保护：

### Protect

```text

Vault 文件被复制

用户自己的云盘泄露加密 Vault

别人直接浏览 App 文件
```

### Cannot Fully Protect

```text
Root / Jailbreak

系统已经被控制

Keylogger

恶意输入法

恶意截屏

高权限恶意软件

用户主动复制密码给攻击者
```

透明意味着也应该告诉用户：

> 本产品不能防御已经完全控制你设备的恶意程序。

# 49. 最重要的技术边界

整个架构可以归纳成：

```text
                       用户
                        │
                        ↓
                ┌───────────────┐
                │  uni-app x UI │
                └───────┬───────┘
                        │
                普通数据 / Command
                        │
                        ↓
                ┌───────────────┐
                │  App Service  │
                └───────┬───────┘
                        │
        ───────────── Security Boundary ─────────────
                        │
                        ↓
                ┌───────────────┐
                │ Native Vault  │
                │               │
                │ Crypto        │
                │ Secure Store  │
                │ Passkey       │
                └───────┬───────┘
                        │
                        ↓
                ┌───────────────┐
                │ Local Vault   │
                │    File       │
                └───────────────┘
```

**UI 可以跨平台。**

**业务逻辑可以共享。**

**数据模型可以共享。**

但是：

> **安全边界不能为了追求跨端复用而牺牲。**

# 50. 架构结论

采用 uni-app x 是可行的，并且比较符合第一阶段需要快速完成 iOS / Android App 的目标。

但项目不应采用：

```text
uni-app x
=
所有东西都跨端
```

而应该采用：

```text
uni-app x
=
统一产品层
+
统一业务模型

UTS / Native
=
安全能力层
```

最终形成：

```text
Transparent Vault

         Shared
           │
    ┌──────┴──────┐
    │             │
Product UI    Domain Core
    │             │
    └──────┬──────┘
           │
     Security Boundary
           │
    ┌──────┴──────┐
    │             │
   iOS         Android
    │             │
 Keychain       Keystore
 Biometrics     Biometrics
 Passkey        Passkey
    │             │
    └──────┬──────┘
           │
     Encrypted Vault
```

这套架构最重要的价值不是“uni-app x 能减少多少代码”，而是：

> **在保持跨端开发效率的同时，把用户真正需要信任的部分压缩到一个很小、可审查、可替换的 Native Security Boundary 中。**

这与整个产品“透明第一，本地第二”的定义是一致的。
